# 交叉审查决定与剩余门槛

日期：2026-09-07。§1–§9 保留各历史审计时点，旧 104/6 和“未实现模型”不代表当前状态；最新为 §10 的模型阶段记录。正文依据、工程推断、诊断证据和实现证据分别记录。

## 1. 可以在正文内确认的部分

### A01：四 VC 与历史文字

Common §2.6（p43–45）规定 UPLI 的 pool/VC 信用及对应返回；§5.8 规定 TL 四个 VC；§8.5.12.1（p233–234）明确安全 SO/SOL 和逐 VC 上下文。Table 2-2 中关于 1.0 的文字不能覆盖这些 2.0 定义。

决定：关闭“2.0 是否只有一个 VC”的疑问。按四 VC 规划；SO 保持每对端、每流跨 VC 顺序，SOL 保持每对端、每流、每 VC 顺序。不把 SO 理解成请求、读响应、写响应三类流之间也必须全局排序。管理 SOL 枚举缺口继续由 A14 跟踪，不能随此问题一并关闭。

### A02：两种模数不是同一个运算

DL/PL §2.6.4.1（p45）还原 Command Flit 的 9-bit 编码；§2.6.6.1（p47）规定有效序号循环 1…511；§2.6.6.3（p48–49）比较有效序号环上的 ACK/replay 距离。

定义三个不同的操作，不能共享一个含糊的 `increment_seq`：

- 有效序号后继：s=511 时为 1，否则为 s+1；0 从不作为新 payload 序号。
- 有效序号环上的距离：`(b-a) mod 511`，非负余数范围 0…510；相同序号的距离必须为 0，不能将距离 0 强行替换成 511。
- 低三位编码还原：先计算低三位差值，payload 的零差值按正文变成 8，再将差值加到上次编码并按 `%512` 还原。

例：511→1 的低三位是 7→1，低位差值为 2，`(511+2)%512=1`。把此处替换为 `%511` 会得到 2，反而出错。此前台账把模数差异整体视作阻塞过于宽泛，现撤回这部分判断。

本轮使用 Node.js v24.17.0 的一次性只读诊断，以显式 `511→1` 遍历和实际队列成员位置作为期望值，未用被检查的模距离公式产生队列期望：

| 检查 | 枚举域 | 数量 | 不一致 |
| --- | --- | ---: | ---: |
| payload 序号还原 | 上次序号 1…511；向前 1…7 个有效 payload 序号 | 3,577 | 0 |
| NOP 序号还原 | 上次序号 1…511；向前 0…6 个有效序号 | 3,577 | 0 |
| ACK/replay 窗口候选 | last_ack 1…511；未确认数 0…255；候选 1…511 | 66,846,976 | 0 |

最后一项每个候选同时比较 ACK 是否属于“last_ack 加当前未确认队列”、replay 是否属于“当前未确认队列”。不是 66,846,976 项协议测试，更不是形式工具证明。NOP 的范围没有延伸到已达到七个坏 flit、必须进入 ambiguous 状态的情况。

决定：上述算术含义已内部确认，可写入后续模型契约；仍需验证 explicit 周期、CRC/ambiguous、重放/重复请求、NOP 与丢包、reset、计时器及所有状态转换。不能把此次结果记为“LLR 已实现/通过”。

### A04、A15：版本溯源与 station 规模

A04 作为已登记的版本历史保留，不单独阻塞。源 PDF 哈希不变，没有用旧标题替换现有 Common/DL/PL 基线。

Common §1.1 p21–22 明确定义 lane 含发送和接收方向，station 为四个 lanes；§2.4 p37 和 §9.2 p246 再次明确四 lanes。§2.5 p41 的孤立“8 lanes”不能作为一个 station 八条双向 lanes 的依据。

决定：四-lane station 的架构/带宽可确认；保留 p41 的文字异常记录，不声称已经获得官方笔误修订。

### A07：GCM 首个数据块编号可以独立确认

Common §8.5.7.3 p212 使用 96-bit IV 并引用 NIST SP 800-38D；§8.5.7.9 p224 将块计数 1 用于标签掩码。[NIST SP 800-38D（2007）§7.1 Algorithm 4](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf)（印刷页 15，PDF 第 23 页）规定此时 `J0 = IV || 0^31 || 1`，数据加密从 `inc32(J0)` 开始，标签掩码使用 `J0`。

决定：标签用计数块 1、首个 128-bit MSG 块用 2；首段 512-bit 数据对应 2…5，与 Common p226–227 的表格一致，不能采用 p225 正文的 1…4。事务级 invocation counter 初值 0 与上述块计数不是一个计数器。此结论只关闭初始块编号问题，不确认 UALink 的完整 AAD/MSG、PCRC 或后续 beat 打包；R036 仍受 A05 阻塞。新增 R042 与独立已知答案/多 beat 检查计划，未运行密码学向量或协议测试。

### A08：换钥必须作用于对应流

Common p216 Figure 8-7 在 Write Response 换钥步骤写成重置 Read Response counter；§8.5.7.5 p219 则逐项规定三条流各自的换钥边界和新派生密钥的首笔事务 IV counter 为 0。p220 Figure 8-9 明确 Write Response 的后续响应采用新密钥并重置该流计数；p221 Figure 8-10 也分开显示三条流切换。

决定：内部确认 Write Response 握手完成后重置的是对应 Write Response 流的 invocation counter，不重新清零已进入新密钥的 Read Response 流。如果读响应在两个握手之间已经发送，再清零读流可能重复使用该流的 `(key, IV)`。p220 重复出现的相同流程框也不能解释成允许隔着业务再次清零。派生密钥可跨流共享，不代表各流同时采用新密钥；epoch、主密钥交换及 SO/SOL 上下文仍按各自条款审查。新增 R043，完整换钥状态机和复位/背压竞态尚未实现验证。

### A11：正向命令分配与保留区间分开处理

Common Table 2-12 p57 显式分配 `0x20=BlockCollectiveInvoke`、`0x21=BlockCollectiveAllocate`、`0x22=BlockCollectiveDeallocate`；§6.3.2–6.3.4 p163–165 又分别规定这些命令的使用。三个值也符合 p57 对 Write 类命令的分类。

决定：可确认这三项显式正向分配，不将其作为保留值拒绝。保留行与正向分配重叠的出版异常仍登记，不将本地推断的替换区间声称为官方勘误，不借此冻结全表负向行为。新增 R044；完整 Block 压缩编解码仍由 A09 阻塞。

### A12：字节使能偶校验的保护集合与公式

Common Table 2-21 p70 的自指文字已经核对原图。§3.1.1 p85 明确 UPLI 的偶校验定义为受保护组连同 parity 位的置位总数为偶数，并要求 OrigDataByteEn 独立校验；§3.1.2 p86 明确 OrigDataByteEnParity 保护该字节使能字段。因此不是只能依赖信号命名作猜测。

决定：内部确认 `OrigDataByteEnParity = XOR-reduce(OrigDataByteEn[63:0])`，仅在 OrigDataVld 有效时检查；保护组不含数据、其它控制字段或自身反馈。校验残差为 64 个 byte-enable 位和收到的 parity 位的归约异或。新增 R041；其保护集合确认不等于错误处置流程全部确认，A17/R040 继续单列。

以上为有交叉依据的内部审查决定，不是联盟回复、官方勘误或实现通过记录。后续仍须以获授权的独立向量/对端检查，不用自研 TX/RX 互相吻合替代互操作证据。

## 2. 纠正及收窄的未决项

### A13：三个层次的端口编号宽度

| 所在层次 | 实际依据 | 不能做的事情 |
| --- | --- | --- |
| 管理序列化 | Manageability Table 4-1 p24：PortNum 映射 uint16/uint16_t；10-bit 描述属于 DeviceId，不属于 PortNum | 不能把 DeviceId 的限制误抄成 PortNum 的定义 |
| DL 消息 | DL/PL §2.4.2.4、Table 2-6 p27–28：端口字段 [27:16]，12 bits | 不能将消息解析器直接缩成 10 bits |
| 安全身份及端点间 IV | Common Table 8-8 p212：端点间 IV 的源端口 [45:36] 为 10 bits；§8.6.1.2 p239 另定义 INC 安全端口身份为 10 bits | 不能将 12/16-bit 端口静默截断为安全身份，也不能将 10-bit 仅归因于 INC |

决定：撤回“管理规范把 PortNum 限为 10-bit”的说法。未决问题收窄为安全配置的可接受范围及跨层映射；默认 profile 可考虑限定受保护端口号 ≤1023，但这是需冻结的配置约束，不是更改 DL 字段。超范围应在配置阶段明确拒绝，不能捏造标准线上错误码。

补充：Table 8-7 p212 的端点间 KMAC context 将源端口填充到 16 bits，不能误写成只有 10-bit context 字段；INC IV（Tables 8-9/8-10）和 INC KDF context（Tables 8-27/8-28）也不能照搬端点间格式。表示宽度、允许值域与上下文拼接是三个不同问题。

### A17：RAS 分歧收窄为错误位置和可隔离性

§3.1.1–3.1.2 p85–86 已将 UPLI OrigDataByteEnParity 错误列入 Data Error。真正仍有分歧的是 §2.7.7.1 p70 对 Switch poison 排除 Byte Enables，而 §3.1.2 p87 又将可独立定位的 Switch Core OrigDataByteEn 错误列入 Data Error。不可区分 data/control 的交换内部错误按 control 处理的要求在 p86–87 是明确的。

决定：R040 收窄为 Switch Core 字节使能错误的分类/处置冲突；独立提取到 R041 的 parity 公式不再等待这一问题。普通写 OrigDataByteEn 与 Atomic 请求控制信息内的 byte mask（§5.3.3 p115）不可混为一谈；未得到澄清前不冻结所有路径的统一 poison/drop 策略。

## 4. 对计划的补充约束

Common §2.4 p37 要求 Pod 中 station 采用相同 bifurcation，各 Accelerator 的端口数相等；§9.2 的独立配置是设备能力，不自动授权同一 Pod 的任意异构宽度部署。计划补入部署一致性检查，避免将 x1/x2/x4 支持列表误解释为所有混搭都合法。不规则 Accelerator 数量与此不是同一个维度。

多 station 补充：用户已批准将 `NUM_STATIONS` 和 `STATION_BIFURCATION` 参数化，见 [交付计划](ip_delivery_plan.md) §2.1/§4.1。Manageability §1.4 Table 1-1 p16 限制每个 Accelerator/Physical Switch 至多 1024 个端口；结合 C §2.4 的 1/2/4 个端口划分，可计算模式相关数量上界，但这不是完整 profile 或物理实现上限。16 仅为此前配置示例；C §9.7 p248 的 64-station 也只是示例，不能固定为标准上限。设备端口数量与 A13 的端口编号范围是独立要求，增加 R045 不关闭 A13。
