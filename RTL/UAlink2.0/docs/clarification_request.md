## 优先问题：直接影响当前完整 profile

### CQ01 / A05 / R036：请求安全映射

位置：C §8.5.1 p198–199，§8.5.7.9 p223–227。

请求概述、字段处理表与详细 AAD/MSG 表对 ReqAddr 位段及 Tag/ASI 是否加密存在差异；p223 的地址 MSG 宽度与标注范围也不一致。

请提供请求在各合法安全模式下的唯一 AAD/MSG 位表，明确 Addr[17:8]、[7:6]、[5:2]、[1:0]，Tag、ASI、byte enables 及 PCRC 的位置/保护方式。需要普通读、部分写、全写、Atomic 和 INC/Block 适用差异，以及单 beat/多 beat 的逐块向量。工程没有把“详细表较自洽”当作官方优先级规则。

答复后的检查：每个相关字段逐位扰动、AAD/MSG 长度、PCRC 开关、跨 beat 拼接、独立密文/tag 已知答案；不能仅做本地加解密往返。

### CQ02 / A06 / R037：响应类型的安全处理

位置：C Table 8-4 p202、Table 8-5 p204，§8.6.5 p242–243。

RdRspTypeInfo/WrRspTypeInfo 的安全处理列为 TBD，而 INC 安全处理使用响应类型区分事务。

请明确两个 TypeInfo 字段是否以及如何进入 AAD/MSG，是否参与密钥/域选择，普通、Collective Primitive、Block 响应如何与 outstanding 事务关联；接收端面对类型扰动或认证失败时，允许发生哪些状态更新？请提供包含类型变化的正/负向向量。

答复后的检查：同 Tag/VC 等其它字段不变时扰动 TypeInfo，不得错选安全域、误关联完成或提前提交数据。

### CQ03 / A09 / R038：BlockRead 压缩响应 FTYPE

位置：C Table 5-27 p136、Table 5-35 p142、Table 5-38 p145。

Table 5-35 的表头为 FTYPE 0x6，字段解释为 0x4；0x4 另有既定响应格式。汇总表未列全 block 扩展，0x7 则有独立格式。

请给出完整且唯一的 FTYPE 解码表，明确单 beat BlockRead 使用的值、与普通 Read/ReadReduce 的区分，以及 0x7 的精确适用类型。请求一个会被另一种候选解释误解码的独立向量，并明确保留值处理。

答复后的检查：格式两两不混淆、不同类型/长度/VC 混排、字段边界和保留值输入；不通过移除接收压缩能力规避问题。

### CQ04 / A10 / R039：FP8 操作编码

位置：C Table 2-5 p54，§6.6–6.7。

0x71 与 0x73 都描述为 FP8 minimumNumber/E4M3。请确认它们是有意别名还是条目错误，并给出 E4M3 maximumNumber 的正式编码及适用数值语义。工程不预设“0x71 应改为 maximumNumber”。

答复后的检查：能区分 minimumNumber/maximumNumber 的操作数；NaN、正负零、无穷/饱和等各数据格式实际支持的特殊值；普通 min/max 与 Number 变体分开。

### CQ05 / A17 / R040：交换内部字节使能错误

位置：C §2.7.7.1 p70，§3.1.1–3.1.2 p85–87，§5.3.3 p115。

p70 的 Switch poison 说明排除 Byte Enables，p87 的 Switch Core Data Error 又包括可以独立定位的 OrigDataByteEn 错误。UPLI parity 的保护集合与交换内部错误处置是不同问题。

请针对普通写 OrigDataByteEn 的可隔离错误，明确 error category、OrigDataError/poison、drop、日志及隔离行为；同时确认不可区分 data/control 的 ECC 错误和 Atomic 控制 mask 错误的适用路径。希望得到按“检测位置 × 可隔离性 × 事务类型”排列的处置矩阵。

答复后的检查：定点翻转与混合 ECC 错误，检查错误传播、内存副作用、信用回收和恢复；不得将所有路径统一 poison 或静默丢弃。

## 配套 profile / 管理面问题

### CQ06 / A13 / R029：端口身份的合法范围与跨层映射

位置：M Table 4-1 p24；L Table 2-6 p28；C Tables 8-7/8-8 p212、§8.6.1.2 p239。

PortNum 管理表示为 uint16，DL 字段为 12 bits，端点间 IV 源端口及 INC 身份描述有 10-bit 定义，端点间 KMAC context 又将源端口填充到 16 bits。请明确各安全模式下允许的端口编号范围、是否允许编号重映射以及该映射的唯一性和配置机制。10-bit 定义不是只存在于 INC；不能直接截断大编号。需要 1023/1024/4095 等边界的配置判据。

### CQ07 / A03、A14 / D02：管理定时器与 SOL schema

位置：M §5.1.1.3 p39–40 的 dead interval 公式；M 端口 OrderingMode；C SO/SOL 定义。

请确认 dead interval 的正式参数来源/计算式，并提供与 Common 2.0 匹配的 OrderingMode 表示及 UALink Control、YANG、SAI 配套资产的准确版本、获取路径、许可和提交标识。基础 OpenConfig gNMI 文件不能替代这些扩展；不自行添加声称属于标准的 SOL 枚举。

### CQ08 / A16：SR-IOV 配置范围

位置：M §2.6 p19；C §7.4 p187。

请澄清 Manageability 单 VF 限制与 Common 同 tenant 多 VF 描述的适用角色及配置层级。单 VF/非虚拟化可先按共同子集规划，但需要正式依据后才能声明多 VF 支持。

## 后续事务/恢复审查问题

### CQ09 / A18 / R097：BlockCollectiveDeallocate 的 drain-only 结束状态

位置：C §6.3.3 p164–165，Figure 6-12；§6.3.4 p167 的 Invoke 接纳条件。两页原图已核对。

p164 明确 DO=1 时 SQ 条目保留分配；p165 的通用流程却在 Deallocate 状态更新完成后将 SQ 置为 unallocated。候选理解是 p165 的释放结尾仅适用于 DO=0，但这没有明确给出 DO=1 的完整分支。

请确认 DO=1 是否保留 SQ 的原分配额度、是否按相同流程停止新 Invoke 和新数据访问、在途/未开始的 Block 如何完成或终止，以及 drain-only 的成功状态和状态写回完成后何时恢复接纳 Invoke。请提供 DO=0 与 DO=1 的分支状态图，以及 drain-only 后立即 Invoke、重复 Allocate、再次 Drain 的合法行为；也请确认状态写回失败时资源保留与恢复责任。

答复后的检查：两模式资源账本、原 Block 状态先于 drain/deallocate 状态的顺序、接纳关闭/恢复边界、状态写回背压与错误；不得通过将 DO=1 等同 DO=0 或删除该能力绕开。R096 只记录已有明确依据的 DO=0 行为，本项不连带阻塞整个 INC 队列的模型研究。

### CQ10 / A19 / R101：DL CRC 的系数、字节及时间位序

依据 L 200G 2.0 Figure 2-4/2-9、§2.3.7 与 Appendix A。640-byte 示例 FH=0x4FFF00（偏移 624–626 为 00 ff 4f，其余全零）经独立长除法和 LFSR 得到多项式系数整数 0xEA3D9002，而 reflected 软件结果为 0x4009BC57。

请确认该示例的 CRC0、CRC1、CRC2、CRC3 的八位值，以及 CRC 第一个/最后一个发送位；如何同时对应正文 x0→x31 和附录打印的 11101010…00000010 时间序列？若所列十六进制采用不同寄存器/系数约定，请提供明确 bit mapping 或正式修订。完整推导见 CRC 位序复现（历史文档已清理）。

暂不冻结 wire encoder/checker；数学子模型继续保留，官方 vector 到位后加入逐位比较与错误接收用例。此问题未发送，未将项目候选解释冒充勘误。
